# Privacy-safe booking confirmation — 9 November 2026

## User journey

The owner approved a generic public confirmation page after successful booking persistence. Checkout and all private booking details remain excluded from GTM. No pricing, payment, enrollment, idempotency, database schema or booking status rule changes.

1. The existing booking API validates and persists, or authorizes an existing replay, exactly as before. Failures and price-change responses do not issue a confirmation handoff.
2. A successful response can attach a short-lived encrypted HttpOnly context and a `/booking-confirmation?flow=<32 hex characters>` URL. The selector is an HMAC of server-owned identity; it is not a booking access token and grants no access without the authenticated cookie.
3. Checkout queues the same authoritative measurement receipt, renders its existing successful receipt and performs the same cart/attempt cleanup. It then acknowledges cookie acceptance with a bounded same-origin **POST** to `/api/bookings/confirmation`. POST supplies Origin even though protected checkout intentionally sends no Referer. The endpoint returns only `{ ready: boolean }`, performs no database operations, limits JSON to 256 bytes and rejects foreign/missing origins.
4. After acknowledgement, a full document navigation enters the generic public page. Existing Advanced Consent Mode, CMS/host restrictions, denied defaults, typed events, ready/reconnection drain, consent proofs and delivered markers apply. No manual return to a catalogue page is needed for this normal success path.
5. The public page shows only generic saved/pending-review/no-online-charge copy in EN/ES/IT. It mounts no SiteShell, live chat, account notifications or private receipt. Its RSC props contain only the public selector. A native form opens `/checkout/receipt` with that selector; the new document remains protected and restores the original receipt/recovery UI. Account receipts require the original current CUSTOMER identity; guest access remains bound to the server-authenticated HttpOnly context and existing private access/recovery mechanisms.

The shared page-view payload uses canonical `/booking-confirmation` and a fixed title, omitting `flow` and every other query value. Private references, email, contact fields and guest links never enter its public DOM/RSC props or analytics payloads. Unknown parameters/fragments remain blocked. Both confirmation documents explicitly use `Cache-Control: private, no-store`; private details also keep `Referrer-Policy: no-referrer` and the existing document/Flight boundary.

## Handoff security and failure behavior

The existing server-only `BOOKING_QUOTE_SECRET` must have at least 32 bytes and remain stable across Node workers. A distinct HMAC-derived key and purpose/version authenticate an AES-256-GCM envelope with a fresh random 12-byte IV. Price-quote tokens are not confirmation tokens. No additional Google credentials, package or migration is introduced.

Cookie: `__Host-sp-booking-confirmation` in production, `HttpOnly`, `Secure`, `SameSite=Lax`, `Path=/`, 30-minute lifetime. Development uses a separate non-prefixed cookie without enabling production tracking. The encrypted context retains only the minimum private receipt snapshot needed to preserve the existing UI/recovery, including a guest email when required; it contains no name, phone, notes or tour item arrays. No private receipt state is added to localStorage/sessionStorage. Existing analytics storage contains only its previously projected safe events/grant metadata.

At most three unexpired contexts fit in a cookie smaller than 3,800 characters. Distinct selectors prevent one tab from opening another tab's booking. Matching guest replays can reuse a prior valid access link; they never mint a replacement guest token for measurement. A missing prior link retains the existing private email-recovery UI. Truly concurrent Set-Cookie responses can overwrite a map; acknowledgement then safely preserves the losing tab's existing successful receipt. This is not a guarantee of concurrent-tab analytics delivery. Expired/evicted/tampered contexts show neutral account/email guidance and never claim the booking failed or invite automatic resubmission.

Missing/short signing configuration, rejected cookies, acknowledgement failures/timeouts (2.5 seconds), unavailable browser APIs, subsequent user navigation and navigation exceptions preserve the original successful checkout receipt. These optional failures do not undo a persisted booking, resubmit it or prevent cart/attempt cleanup. Restored details are a short-lived receipt snapshot; the existing booking details APIs remain responsible for current status, payment authorization, token revocation and account ownership.

HttpOnly protects direct cookie reads; it is not a sandbox against arbitrary same-origin JavaScript. Keep the published-container restrictions, native consent-aware Google tags, and disabled automatic form/user-provided-data collection. Existing Google account configuration remains an external trust boundary.

## Measurement and release contract

- Existing `sp_booking_created`, `event_id`, `items`, authoritative USD value and captured/current Analytics/Marketing proof semantics remain unchanged. This is a **booking lead**, never `purchase` or proof of payment.
- The confirmation drains the existing queue; it does not create another measurement event or another GA4 loader. Refresh/recovery reuse delivered markers. Analytics-only leads cannot become Ads-eligible from a later Marketing grant. Rejection/withdrawal continues to block application events.
- `sp_begin_checkout` retains its existing private capture/deferred drain semantics. A visitor who abandons checkout before any later public document may remain unmeasured for that milestone.
- Google blocked by consent/storage/network/ad blockers, closing the page before loading, handoff fallback and missing published tags can still prevent optional measurement. Queue dispatch is not a Google delivery acknowledgement or a guarantee of GA4 custom-event deduplication.
- Publish one native Google tag for the intended GA4 destination and an exact `sp_booking_created` Custom Event trigger/tag with the existing variables and consent checks. Ads leads additionally require `ads_eligible === true`, current Marketing consent and the stable `event_id` mapped to transaction/order ID. Keep one page-view strategy; do not change the explicit flag here. GTM Preview should find the public confirmation container; **Checkout itself intentionally remains tag-free**.
- Verify the existing signing configuration, publish the application normally, then verify the published Google container and isolated Preview/DebugView. No live events, bookings, Google changes or deployment were performed during implementation. Repository rules prohibit browser automation, so browser appearance and live delivery are not claimed as verified.

Local checks cover encrypted context integrity/expiry/ownership, replay and bounded multiple contexts, no-Referer POST acknowledgement, fallback/timeouts, generic EN/ES/IT rendering, private document boundaries, success/failure/price responses, consent, multi-tour lead drain and refresh deduplication. Production build verification uses the isolated compile-only mode with an unreachable database URL; full database-backed generation is not part of this check.
